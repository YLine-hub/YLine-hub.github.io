Introduction to RAG

Limitations of large

(1) Outdated knowledge

Because LLMs have massive parameters, pretraining and fine-tuning require considerable resources and time. In addition, commercial LLMs also need to undergo various security tests and risk assessments. As a result, LLMs suffer from outdated knowledge.

(2) Missing knowledge

In specialized domains, LLMs cannot learn all the details of professional knowledge, so they cannot provide reliable and accurate answers to domain-specific questions.

(3) AI hellucination

When generating responses, LLMs may “talk nonsense.” This phenomenon is called LLM “hallucination.” Hallucination can manifest as false statements, fabricated facts, incorrect complex reasoning, or insufficient comprehension in complex contexts.

Causes of “hallucination”:

  1. The training knowledge contains biases, and these erroneous pieces of information are learned by the LLM and reproduced in its output (e.g., incorrect encyclopedia entries, outdated information, fake papers, buggy code).

  2. LLMs overgeneralize during training, applying general patterns to specific situations and producing inaccurate output.

  3. LLMs do not truly learn the deeper meaning of the training data, which leads to errors in tasks requiring deep understanding or complex reasoning.

  4. LLMs lack knowledge in certain domains and fabricate nonexistent information when faced with questions in those domains.

What is RAG

Definition of RAG: To address the shortcomings of large models in timeliness, reliability, and accuracy, various optimization methods for LLMs have emerged. RAG (Retrieval-Augmented Generation) is one such optimization architecture that has been widely studied and applied.

The basic idea of RAG is to combine traditional generative large models with real-time information retrieval technology, supplementing the model with relevant external data and context to help it generate more accurate and reliable content. This allows the model to rely on real-time and personalized data and knowledge when generating content, rather than only on its training knowledge. It is like giving the model a reference book when it answers questions

Pros and cons of RAG

(1) Advantages of RAG

  1. Compared with prompt engineering, RAG has richer context and data samples, so it can generate answers that better meet user expectations without requiring the user to provide too much background information.

  2. Compared with model fine-tuning, RAG can improve the timeliness and reliability of question-answering content.

  3. To some extent, it protects the privacy of business data.

(2) Disadvantages of RAG

  1. Since each Q&A involves data retrieval from external systems, RAG has relatively high response latency.

  2. The external knowledge data being referenced consumes a large amount of model token resources.

RAG workflow

(1) A typical RAG has two main processes:

  1. Indexing: extract data from data sources and build an index.

  2. Retrieval and generation: accept the user query, retrieve relevant data from the index, and then pass it to the model.

(2) The overall indexing process is as follows:

  1. Load data from various data sources;

  2. Split the document into small chunks;

  3. Embed the text chunks;

  4. Store the embedding vectors.

(3) Retrieval and generation stage:

  1. Based on the user input, use the retriever to retrieve relevant text chunks from storage;

  2. The large model uses a prompt containing the question and the retrieval results to generate an answer.

Document loading

Data sources may contain files in various formats, such as text documents, Markdown, and PDFs. Therefore, we first need to process files in these different formats. LangChain implements and integrates many document loaders, making it easy to load data from files in different formats. You can view all integrated document loaders at https://docs.langchain.com/oss/python/integrations/document_loaders.

All LangChain document loaders implement the BaseLoader interface, which provides the common load() method (loads all documents at once) and lazy_load() method (loads documents lazily), used to load data from data sources and process it into Document objects.

LangChain implements the Document abstraction to represent a unit of text and its metadata. It contains three attributes:

  • page_content

  • metadata

  • id

    # mode="elements" 表示将文档加载成List[Document]列表，自动根据标题，列表，表格分割

def enrich_document_info(document_list: list[Document])->List[dict[dict,str]]:
    # Stack, used to store historical titles
    stack = []          # Stack: last in, first out(LIFO)  , Queue: first in, first out (FIFO)
    category_depth = 0
    """
    [
        {
            "meta_data": {},
            "content": "一级标题" > "二级标题" + "\n" + "正文"
        }
    ]
    """
    enriched_list = []  # Used to store the processed document

    # 对文档进行迭代
    for doc in document_list:
        # 如果类型是标题
        if doc.metadata['category'] == 'Title':
            # 获取标题级别
            category_depth = doc.metadata['category_depth']
            # [(0,"一级标题"),(1,"二级标题")]       标题1-6个级别
            # 当栈不为空，并且栈里面的最后一个元组的第一个元素，比如这里 [(0,"一级标题"),(1,"二级标题")]  为 1
            # 将这个标题级别及其之后的级别全部弹出
            while stack and stack[-1][0] >= category_depth:
                stack.pop() # 最后进栈的删除
            stack.append((category_depth, doc.page_content))    # Tuple[int, str]
        else:
            # [for category_depth, doc.page_content in stack]
            # [title for _, title in stack]       # 表示前一个数据丢弃，只要后一个数据，作为title返回
            level_title_info = ">".join([title for _, title in stack])

            doc_dict = {
                "meta_data": doc.metadata,
                "content": level_title_info + "\n" + doc.page_content
            }

            enriched_list.append(doc_dict)
    return enriched_list

if __name__ == '__main__':
    document = markdown_load_demo()
    enrich_doc_list = enrich_document_info(document)
    for doc_dict in enrich_doc_list:
        print(doc_dict['content'])
        print("=" * 50)

def mineru_upload_file_demo():
    import requests

    token = os.getenv("MINERU_TOKEN")

        "Authorization": f"Bearer {token}"
    }
    data = {
        "files": [
            {"name": "sample.pdf", "data_id": "abcd"}  # 告诉服务端我要上传的文件名
        ],
        "model_version": "vlm"
    }
    file_path = [r"/Users/line/PycharmProjects/Langchaingrape/assets/sample.pdf"]  # 真正要上传的文件
    try:
        response = requests.post(url, headers=header, json=data)  # "告诉服务器我要上传什么文件"，服务器返回临时上传地址
        if response.status_code == 200:
            result = response.json()
            print('上传成功:{}'.format(result))

            if result["code"] == 0:
                batch_id = result["data"]["batch_id"]
                urls = result["data"]["file_urls"]
                print('batch_id:{},urls:{}'.format(batch_id, urls))
                for i in range(0, len(urls)):
                    with open(file_path[i], 'rb') as f:
                        res_upload = requests.put(urls[i], data=f)  # "把文件真正传上去"
                        if res_upload.status_code == 200:
                            print(f"{urls[i]} 上传成功")
                        else:
                            print(f"{urls[i]} 上传失败")
            else:
                print('apply upload urlfailed,reason:{}'.format(result.msg))
            return batch_id
        else:
            print(f"请求失败，状态码：{response.status_code}，响应内容： {response.text}")
    except Exception as err:
        print(err)

Document chunking

RecursiveCharacterTextSplitter

RecursiveCharacterTextSplitter is the most commonly used splitter. It takes a list of characters as a parameter, with the default list being ["\n\n", "\n", " ", ""]. It tries to split using these characters in order until the chunks are small enough. In this way, it keeps all paragraphs (then sentences, and finally words) together as much as possible, since these paragraphs usually appear to be the most semantically relevant text fragments.
At the same time, to ensure semantic integrity between chunks, you can set a certain amount of overlap between each chunk.

Vector storage and retrieval

Understanding vector databases

Suppose you are a photographer and have taken a large number of photos. To make them easier to manage and search, you decide to store these photos in a database. Traditional relational databases (such as MySQL, PostgreSQL, etc.) can help you store photo metadata, such as the time taken, location, camera model, and so on.

However, when you want to search based on the content of the photos (such as color, texture, objects, etc.), traditional databases may not meet your needs, because they usually store data in tables and use query statements for exact searches. At this point, vector databases come into play.

We can build a multidimensional space in which the features of each photo exist and are represented by existing dimensions, such as time, location, camera model, color, and so on. The information of this photo is stored as a point within it.

By extension, countless points can be constructed in this space, and then these points are connected to the origin of the spatial coordinate axes, becoming vectors. Once these points become vectors, vector computation can be used to obtain more information. When retrieving photos, it also becomes easier and faster.

Note that when searching in a vector database, you are not retrieving a single exact match, but rather the vectors most similar to the target vector, which is inherently fuzzy.

As an extension, as long as images, videos, products, and other materials are vectorized, functions such as image-based image search, video-related recommendations, and similar product recommendations can be achieved.

Milvus Collection and Data Types

Milvus manages data through the structure of database → collections → entities. Collections and entities are similar to tables and records in relational databases. Specifically, a collection is a two-dimensional table with fixed columns and variable rows. Each column represents a field, and each row represents an entity.

The following are the data types supported by Milvus:

向量字段密集向量FLOAT VECTOR32 位浮点数列表

The vector field is the most important field and can be divided into dense vectors or sparse vectors.

Dense vectors are typically generated by deep learning models based on the Transformer Encoder architecture, such as Sentence-BERT.

Sparse vectors are used to represent keywords in text and their corresponding weights. Their construction has evolved from traditional bag-of-words models based on statistical methods such as TF-IDF (Term Frequency–Inverse Document Frequency) to today’s learned construction methods based on deep learning models.

# Create a schema           Collection ( table ) structure
def create_collection_schema(client: MilvusClient) -> CollectionSchema:
    return (client.create_schema(
        # 自动为 id 字段赋值
        auto_id=True).add_field(field_name="id", datatype=DataType.INT64, is_primary=True)  # 主键，必须是int64或varchar类型
            .add_field(field_name="dense_vector", datatype=DataType.FLOAT_VECTOR, dim=1024) # 稠密向量字段
            .add_field(field_name="sparse_vector", datatype=DataType.SPARSE_FLOAT_VECTOR)   # 稀疏向量字段
            .add_field(field_name="text", datatype=DataType.VARCHAR, max_length=65535)  # 标量字段，即普通字段
            .add_field(field_name="metadata", datatype=DataType.JSON, max_length=65535)  # 标量字段，即普通字段
    )

# Index settings
def create_collection_index(client: MilvusClient):
    index_params = client.prepare_index_params()
    index_params.add_index(
        field_name="dense_vector",  # 字段名字
        index_type="HNSW",  # 分层导航小世界
        metric_type="L2",   # L2        欧几里得距离  相似度匹配：度量方式          也可以选择：余弦相似度 COSINE
    )

    index_params.add_index(
        field_name="sparse_vector", # 字段名字
        index_type="SPARSE_INVERTED_INDEX", # 倒排索引      参考 Elasticsearch    搜索引擎
        metric_type="IP",   # IP    内积          负无穷 ～ 正无穷   归一化处理 [0, 1]
    )

    return index_params

# Create a collection
def create_collection(client: MilvusClient, collection_name: str = "demo_collection"):
        if client.has_collection(collection_name=collection_name):
            client.drop_collection(collection_name=collection_name)

        client.create_collection(
            collection_name=collection_name,
            schema=create_collection_schema(client),
            index_params=create_collection_index(client)
        )

        print(client.list_collections())

        print(client.describe_collection(collection_name=collection_name))

if __name__ == '__main__':
    client = get_milvus_client()
    create_collection(client)

from typing import List

from langchain_community.document_loaders import UnstructuredWordDocumentLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter
from langchain_core.documents import Document
from pymilvus import MilvusClient
from FlagEmbedding import BGEM3FlagModel
import json

def get_milvus_client():
    """创建Milvus客户端"""
    return MilvusClient(uri="http://192.168.1.109:19530", token="")

def insert_data(client: MilvusClient):
    """向量数据库保存数据"""

    # 1. 加载docx
    document = UnstructuredWordDocumentLoader(file_path="../assets/sample.docx", mode="single").load()

    # 2. 递归字符分割器
    recursive_char_splitter = RecursiveCharacterTextSplitter(
        chunk_size=400,
        chunk_overlap=50,
        length_function=len,
        separators=["\n\n","\n","。","！","？",""]
    )

    # 切片
    chunks: List[Document] = recursive_char_splitter.split_documents(document)
    chunks = chunks[0:20]
    # 向量化
    bgem3_client = BGEM3FlagModel("../assets/models/bge-m3", return_dense=True, return_sparse=True)
    resp = bgem3_client.encode([doc.page_content for doc in chunks])

    dense_vecs = resp['dense_vecs']
    sparse_vecs = resp['lexical_weights']

    # 4. 实体封装
    """
        参考数据结构
        [
            {page_content='第二编　物权...第一分编　通则' metadata={'source': '../assets/sample.docx', 'start_index': 346}}
            {page_content='第二编　物权...第一分编　通则' metadata={'source': '../assets/sample.docx', 'start_index': 346}}
        ]
    """
    entities = []   # 多行数据
    for doc, dense_vector, sparse_vector in zip(chunks, dense_vecs, sparse_vecs):
        entity = {  # 一个字典就是一个实体对象，就是一行数据
            "text": doc.page_content,                   # 原内容
            "metadata": doc.metadata,                  # 元信息   JSON ，转换成JSON字符串
            "dense_vector": dense_vector,               # 稠密向量
            "sparse_vector": sparse_vector              # 稀疏向量
        }
        entities.append(entity)

    # 5. 批量存储
    milvus_client = get_milvus_client()

    resp = milvus_client.insert(collection_name="demo_collection", data=entities)
    print(f"数据保存成功条数:{resp.insert_count}")

if __name__ == "__main__":
    insert_data(get_milvus_client())

from typing import Any, Dict, List, Tuple

COLLECTION_NAME = "demo_collection"


def get_milvus_client(uri: str = "http://192.168.1.109:19530", token: str = ""):
    from pymilvus import MilvusClient
    return MilvusClient(uri=uri, token=token)


def get_bge_m3_model():
    from FlagEmbedding import BGEM3FlagModel
    return BGEM3FlagModel(model_name_or_path="../assets/models/bge-m3")


def encode_query(model, query: str) -> Tuple[List[float], Dict[int, float]]:
    all_embeddings = model.encode([query], return_dense=True, return_sparse=True)
    dense_vec = all_embeddings["dense_vecs"][0]
    sparse_vec = all_embeddings["lexical_weights"][0]
    return dense_vec, sparse_vec


def print_hits(title: str, hits: List[dict]):
    print("\n" + "=" * 20)
    print(title)
    print("=" * 20)
    for i, hit in enumerate(hits, start=1):
        entity = hit.get("entity", {})
        print(
            {
                "rank": i,
                "id": entity.get("id"),
                "distance": hit.get("distance"),
                "text": entity.get("text"),
                "metadata": entity.get("metadata"),
            }
        )


def dense_vector_search_example(client, query: str, limit: int = 5):
    model = get_bge_m3_model()
    dense_vec, _ = encode_query(model, query)
    results = client.search(
        collection_name=COLLECTION_NAME,
        data=[dense_vec],       # 查询条件
        anns_field="dense_vector",  # 稠密字段名称
        limit=limit,    # 返回 Top k
        search_params={"metric_type": "L2"},    # HNSW 索引，查找数据范围，根据L2欧几里得距离获取分数高的文档
        output_fields=["id", "text", "metadata"],
    )
    print_hits("稠密向量检索（vector）", results[0])
    return results


def sparse_vector_search_example(client, query: str, limit: int = 5):
    model = get_bge_m3_model()
    _, sparse_vec = encode_query(model, query)
    results = client.search(
        collection_name=COLLECTION_NAME,
        data=[sparse_vec],  # 查询条件， 安装稀疏向量查询        看关键词    权重      BERT
        anns_field="sparse_vector", #   稀疏向量字段
        limit=limit,    # 返回 Top K
        search_params={"metric_type": "IP"},    # 采用内积打分
        output_fields=["id", "text", "metadata"],     # 返回字段
    )
    print_hits("稀疏向量检索（sparse_vector）", results[0])
    return results


def hybrid_vector_search_example_rrf(client, query: str, limit: int = 5):
    """混合向量检索"""
    from pymilvus import AnnSearchRequest, RRFRanker
    model = get_bge_m3_model()
    dense_vec, sparse_vec = encode_query(model, query)

    # 第一路检索
    dense_req = AnnSearchRequest( # 近似紧邻相似度查询
        data=[dense_vec],
        anns_field="dense_vector",
        param={"metric_type": "L2"},
        limit=limit,

import os
from typing import Tuple, List, Dict

from dotenv import load_dotenv
from langchain_openai import ChatOpenAI
from pymilvus import MilvusClient, AnnSearchRequest, RRFRanker
from FlagEmbedding import BGEM3FlagModel

load_dotenv()
COLLECTION_NAME="demo_collection"

def get_milvus_client(uri: str="http://192.168.1.109:19530", token: str=""):
    return MilvusClient(uri=uri, token=token)

def get_bge_m3_model():
    return BGEM3FlagModel(model_name_or_path="../assets/models/bge-m3")

def encode_query(model, query: str) -> Tuple[List[float], Dict[int, float]]:
    all_embeddings = model.encode([query], return_dense=True, return_sparse=True)
    dense_vec = all_embeddings["dense_vecs"][0]
    sparse_vec = all_embeddings["lexical_weights"][0]
    return dense_vec, sparse_vec

def hybrid_vector_search_example_rrf(client: MilvusClient, query: str, limit: int=5):
    model = get_bge_m3_model()
    dense_vec, sparse_vec = encode_query(model, query)

    dense_req = AnnSearchRequest(
        data=[dense_vec],
        anns_field="dense_vector",
        param={"metric_type": "L2"},
        limit=limit
    )

    sparse_req = AnnSearchRequest(
        data=[sparse_vec],
        anns_field="sparse_vector",
        param={"metric_type": "IP"},
        limit=limit
    )

    results = client.hybrid_search(
        collection_name=COLLECTION_NAME,
        reqs=[dense_req, sparse_req],
        ranker=RRFRanker(60),
        limit=limit,
        output_fields=["id","text","metadata"]
    )
    print("混合向量检索（RRF 融合稠密+稀疏）", results[0])
    return results
