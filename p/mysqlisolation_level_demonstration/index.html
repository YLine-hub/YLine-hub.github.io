Demonstration

READ UNCOMMITTED (demonstrate dirty read)

Dirty read : Transaction A reads uncommited changes made by Transaction B. If B roll back, the data A read is invalid.

Point in time Session A Session B
T1 set session transaction isolation level read uncommitted;
T2 start transaction; set session transaction isolation level read uncommitted;
T3 start transaction;
T4 update account set balance = 2000 where id = 1;
T5 select balance from account where id = 1; => Read 2000 (dirty read)
T6 rollback;
T7 select balance from account where id = 1; => It changes back to 1000

The 2000 that session A reads at T5 is uncommitted data from Session B. After B roll back, the data disappears —— this is a dirty read

READ COMMITTED (Demonstrate non-repeatable read)

Non-repeatable read : within the same transaction, reading the same row twice yields different results because another transaction committed a modification in between

Point in time Session A Session B
T1 set session transaction isolation level read committed;
T2 start transaction;
T3 select balance from account where id = 1; => 1000
T4 update account set balance = 2000 where id = 1;
T5 commit;
T6 select balance from account where id = 1; => 2000(different from T3)

Session A made no changes, yet the two reads returned inconsistent results —— this is a non-repeatable read

REPEATABLE : (MySQL default)

Repeatable read : within the same transaction, reading the same row multiple time always yields consistent results, even if other transactions have committed changes. InnoDB achieves this through MVCC snapshots.

Point in time Session A Session B
T1 set session transaction isolation level prepeatable read;
T2 strat transaction;
T3 select balance from account where id = 1; => 1000
T4 update account set balance = 2000 where id = 1;
T5 commit;
T6 select balance from account where id = 1; => 1000
T7 commit;

Session A still reads 1000 at T6, because the MVCC snapshot was already established at its read in T3

SERIALIZABLE : (Serializable)

Serializable : all ordinary select statements are automatically converted to select … for share (acquiring shared locks). Reads and writes are mutually exclusive, and transactions are excuted serially. This completely prevents phontam reads, but has the lowest concurrency performance.

Point in time Session A Session B
T1 set session transaction isolation level serializable;
T2 start transaction;
T3 select * from account where id = 1;
T4 update account set balance = 2000 where id = 1; => blocked
T5 commit;
T6 update executed successfully

Session B’s update will be blocked until Session A commits.

Comparison summary of the four isolation levels

Isolation level Dirty read Non-repeatable read Phantom read Concurrency performance
READ UNCOMMITTED Possible Possible Possible Highest
READ COMMITTED Avoid Possible Possible Relatively high
REPEATABLE READ Avoid Avoid InnoDB Avoid Medium
SERIALIZABLE Avoid Avoid Avoid Lowest

MySQL InnoDB’s default isolation level is REPEATABLE READ, which strikes a good balance between consistency and concurrency.
